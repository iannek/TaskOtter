# TaskOtter 要件

この文書の第1～6節と第8節を、初版の要件と対象範囲の正本とする。初期メモ `notes/タスク管理ツール.md` と、その後の対話で確認した判断を統合した。第7節は将来の候補、第9節は未決の要件、第10節は要件とは分けた運用・設計・検証への引き継ぎである。

## 1. 目的

- ツールの正式名称は「TaskOtter」とする。
- 仕事で使う個人用のタスク管理ツールを作る。
- 会社で利用できる既存ツールの機能の過不足と、ObsidianなどMarkdown中心の管理における操作性・可視性・動作の重さを改善する。
- ローカルで動くブラウザUIにより、タスクの登録、状況確認、予定変更を直感的に行えるようにする。
- 構造化されたファイルを保存形式とし、GitHub CopilotなどのAIからタスクデータを読み取り・更新できるようにする。
- 特に起動時と一覧・画面切り替え時の軽さを重視する。

## 2. 初版の範囲と利用・技術上の制約

- 初版には、Task・Outcomeの登録と管理、ダッシュボード、ガントチャート、カレンダーを含める。
- アプリケーションはコンテナで動かす。WindowsではPowerShellからWSL組み込みのwslc.exeを直接呼び出し、同じPCのWindowsブラウザを使用する。この方式ではUbuntuの導入・起動は前提としない。代替としてWSL Ubuntu内のDocker Engineからも起動できる。MacではApple containerから起動し、同じMacのブラウザを使用する。
- 初版の接続範囲は同じPCに限る。LAN内の別端末やインターネットからのアクセスは想定しない。
- データ保存先にはホスト（WindowsまたはMac）上の任意のディレクトリを指定できる。保存先はコンテナ起動時に指定し、変更するときは再起動する。
- データベースは用意せず、初版ではAIから直接読み書きできるJSON形式でデータを保存する。

## 3. 管理するデータとルール

### 3.1 Task

| 項目 | 要件 |
| --- | --- |
| タスク名 | 登録する。名前だけを入力して素早くTaskを作成できる。 |
| メモ | Markdownの編集とプレビューを切り替えられる自由記述欄。対応履歴は記載例の一つ。ツールから編集でき、承認後にAIがJSONを直接更新することも想定する。 |
| カテゴリ | 任意の分類名を表す。使用中のカテゴリ一覧から選ぶか、「新しいカテゴリを作成」で入力する。カテゴリなしも選べる。タスク保存時に確定する。 |
| ステータス | `Inbox`、`NextAction`、`Waiting`、`Doing`、`Done`、`Someday`。名前だけで登録する場合の初期値は`Inbox`。完了状態は`Done`。 |
| 締切日 | カレンダーから日付を選択できる。 |
| 対応予定期間 | 締切日と同じ日付選択欄で開始日・終了日を設定する。開始日だけなら終了側を自動的に「以降」、終了日だけなら開始側を自動的に「以前」とする。両方未設定なら期間なし。締切日とは別の項目とする。 |
| 次の対応予定 | Taskに実際に取り組む時間として、日付と開始時刻・終了時刻を指定できる。開始と終了は同じ日付内とし、終了時刻は開始時刻より後にする。全ステータスで編集できる。 |
| 次の予定で行うこと | 次の対応予定の日時の下に、その時間で行う作業内容を記載する。 |
| サブタスク | 名前と完了チェックを持つチェックリスト。追加・削除でき、親Taskの完了には自動連動しない。 |
| 資料リンク・関連チャット | それぞれ別タブで、リンク先と概要のボックスを複数追加・削除できる。資料はSharePoint・外部URL・ローカルの絶対パスを想定。 |
| Outcomeとの紐づけ | 既存のOutcomeに紐づけられる。紐づけないTaskも登録できる。 |

- 締切日、対応予定期間、次の対応予定はいずれも任意であり、全ステータスのTaskをこれらが全て空欄のまま登録・変更できる。
- 次の対応予定の開始・終了時刻は、入力欄をクリックして開く小さなポップアップから選択する。選択間隔は15分を初期値とし、設定で30分に変更できる。
- 「以前」「以降」を明示的に選ぶ操作は設けない。保存形式のbefore / afterは維持し、外部JSONの両端無期限データも表示・判定できる。
- Outcomeの対応期間からTaskの対応予定期間がはみ出しても、登録・変更は可能とする。設定時と設定後の両方で、はみ出しを視覚的に警告する。

### 3.2 Outcome

- 複数のTaskをまとめる単位とする。アウトカム名、メモ、対応期間、完了フラグを持つ。
- 対応期間は紐づくTaskの日付から算出せず、独立して設定する。期間が未定のままでも登録できる。
- 紐づくTaskの一覧と各Taskのステータス状況を自動表示する。Outcome自体にTaskと同様のステータスは持たせない。
- 完了フラグは手動で付ける。紐づくTaskに`Done`以外が残っている間は付けられない。全てのTaskが`Done`になっても自動では付けない。
- 紐づくTaskが0件の場合も、手動で完了フラグを付けられる。
- 完了フラグを付けた後、紐づくTaskを`Done`以外に戻すか、`Done`以外のTaskを新たに追加・紐づけした場合は、完了フラグを自動で外す。

### 3.3 削除と復元

- Outcomeを削除しても、紐づくTaskは削除しない。TaskからOutcomeとの紐づけだけを外す。
- TaskやOutcomeの削除後、ツール内から復元する機能は初版に含めない。外部のファイルバックアップから復元できれば十分とする。

## 4. 画面と操作

### 4.1 ダッシュボード

- `Done`のTask数を完了数として表示する。
- 残タスク数には`Inbox`、`NextAction`、`Waiting`、`Doing`を含め、`Someday`と`Done`は含めない。
- 今日が対応予定期間内にあるTaskを表示する。開始日・終了日の両端を含む。開始側が「以前」なら終了日以前、終了側が「以降」なら開始日以降、両方を選んだ場合は常に期間内と判定する。`Done`のTaskは表示しない。
- 「次の対応予定」に時間帯が設定されたTaskを、過去の予定も含めて全件表示する。日付と開始・終了時刻を表示し、`Done`のTaskは除外する。日付フィルターで絞り込めるようにし、初期表示順は開始日時の古い順とする。

### 4.2 Task・Outcome画面

- Task一覧とOutcome一覧を別メニューにせず、一つの「Task・Outcome」画面にまとめる。
- 同じ画面内で「階層一覧」と「Outcomeカード」をタブで切り替えられる。
- 階層一覧ではガントチャートと同様にOutcomeを親行、その下に紐づくTaskを子行として表示する。紐づかないTaskは「Outcomeなし」の親行の下に表示する。
- Outcomeカードのタブでは、Outcomeごとにカード表示する。

### 4.3 ガントチャート

- Outcomeを親行として、その独立した対応期間とともに表示する。紐づくTaskをその下の子行に表示する。
- Outcomeに紐づかないTaskは「Outcomeなし」のまとまりに表示する。
- 対応予定期間が未設定のTaskはバーなしの行として、対応期間が未設定のOutcomeはバーなしの親行として表示する。
- Taskを選択するとサイドバーに詳細を表示し、そこから対応予定期間、締切などを編集できる。
- Taskのステータスとカテゴリで表示を絞り込める。絞り込み後に子Taskが一つも表示されないOutcomeは、完了フラグがあれば非表示、なければ表示する。
- Taskの表示順は名前、ステータス、カテゴリから選べる。
- Taskの期間がOutcomeの対応期間からはみ出していることを、表示中も分かるようにする。

### 4.4 カレンダー

- 日・週・月の単位で表示できる。週は日曜日始まりとする。
- 日・週表示では、日付を横方向の列に並べ、縦方向に0:00から24:00までの時間軸を置く。次の対応予定を、その日付の開始時刻から終了時刻までの範囲として表示する。
- Taskの締切日と次の対応予定をそれぞれ表示する。
- `Done`のTaskは通常非表示にし、フィルターを外すと表示できるようにする。

### 4.5 共通操作・日付表示（2026-10-02追加）

[確認結果・追加要望](確認結果・追加要望.md) に記載された追加要望を初版に反映する。

- Task・Outcomeの編集サイドバーは、サイドバー外の画面をクリックして閉じられる。
- 編集サイドバーの幅は左端のドラッグで調整できる。
- ガントの日付見出しは、カレンダーの週表示と同じ `9/29(火)` 形式とする。
- 締切日・期間・次の対応予定・日付フィルターの選択欄は、年・月・日を別々のクリック対象にせず、日付全体を一つのクリック対象とする。
- 対応予定期間／対応期間が未設定の場合の表示は `-` とする。

## 5. JSON保存とAIによる更新

### ツールに求める動作

- 普段の編集をブラウザUIから行える。初版から、ツール外のAIが保存先のJSONにTaskやOutcomeを直接追加・更新した場合も、そのデータを読み込める。
- ツール外で更新されたJSONは、ブラウザを再読み込みすると画面に反映される。開いている画面への自動反映は必要ない。
- AI更新後のブラウザ操作では、後から保存した内容を優先する。編集の競合検知や差分統合は初版の要件としない。
- JSONの構文または定義済みのデータ仕様に適合しないことを読み込み時に検知したら、画面にエラーを表示する。エラーを検知している間はツール上の編集・保存を無効化し、元のJSONを上書きしない。ファイルを修正して正常に再読み込みできた後に編集・保存を再開する。
- ツール内にAI機能やAI更新案の承認画面は設けない。

## 6. 性能要件

- 数百件のTaskを扱う状態でも利用できること。
- 起動済みのツールをブラウザで開いてから一覧が表示されるまでと、一覧・ダッシュボード・ガントチャート・カレンダーの切り替え時に、重さを感じにくいことを重視する。
- 数百件のTaskがある状態で、起動済みのツールをブラウザで開いてから一覧が表示されるまで、および一覧・ダッシュボード・ガントチャート・カレンダーの画面切り替えにかかる許容時間は、それぞれ5秒以内とする。

## 7. 初版の後に追加する候補

- ダッシュボードのカテゴリ別・ステータス別の円グラフ。
- ガントチャートの任意のカスタム表示順と、GUI操作による行の入れ替え。
- ガントチャート上でバーや締切を直接操作する編集。初版ではサイドバーから編集する。
- カレンダー上の日時を直接クリックし、Taskを追加する操作。
- カレンダー上のTaskを動かし、次の対応予定を変更する操作。
- 毎週・毎月などのTaskの繰り返し作成。初版は必要な都度登録する。
- 複数端末での利用。利用する場合も各端末のローカルにデータを置き、GitHubやiCloudなど外部の仕組みで共有する案がある。Cloudflareなどへの配置も可能性として挙がっているが、具体的な方式は未決定。

## 8. 初版で追加しない機能

- ブラウザを開いていないときの通知。締切日や次の対応予定は画面を開いて確認できればよい。
- ツール内での削除データの復元。復元は外部のファイルバックアップを利用する。
- タスク管理ツール内でのAI更新案の承認操作。

## 10. 運用・設計・検証への引き継ぎ（要件ではない）

### 想定するツール外の運用

- Obsidianに自然な文章で作業記録を残す。GitHub CopilotなどのAIが記録とTaskデータを読み、ステータス変更やTaskメモへの対応履歴追記の案を作る。対応履歴はメモの記載例であり、メモの用途を限定しない。
- ユーザーはAIとの対話内で対象Taskと更新内容を確認・承認し、その後AIがJSONを更新する。AIは自動実行しない。
- AIがどのTaskを対象とするか、作業記録をどう解釈してステータスを判断するかは、AI側のスキル・プロンプトとユーザーの承認で扱う。同じ記録の再処理による履歴の二重追記も承認時に確認する。

### 採用済みの暫定設計方針

- 初版はTaskとOutcomeを一つのJSONファイルにまとめる。数百件のデータを扱う際の速度を確認し、必要なら見直す。

### 画面試作での仮置き

- 日・週カレンダーでは、時刻を持たない締切日を各日付列の上部に置く。次の対応予定は開始時刻から終了時刻までの範囲に置く。

### 設計時に決める事項

- JSON内部の構造：Task・Outcomeの識別子、任意項目や日付・日時の表現、紐づけと履歴の表現。
- 検証の実現方法：データ仕様への適合判定、親子関係や完了条件の検証方法、エラーの示し方。
- 使用する言語、ライブラリ、アーキテクチャ。

### 開発・検証時の前提

- 開発には基本的にAIを用いる。
- 実際に使用するWindows上の保存先を使い、数百件のTaskがある状態で起動と画面切り替えの速度を測る。


## 2026/10/02追加：行の操作

- Task行の名前・カテゴリ・空白部分から詳細サイドバーを開く。ダッシュボード、Outcomeカード、階層一覧、ガントのTask行を対象とする。
- 階層一覧のステータスは行上の選択欄から変更し、その時点で保存する。対応予定期間・締切日・次の対応予定は該当欄から行内編集を開き、「保存」で確定する。「キャンセル」は未保存の変更を破棄する。編集操作では詳細サイドバーを開かない。
- Outcomeの対応期間は従来どおり両端の日付を設定するか、両端を未設定とする。


## 2026/10/02 18:00追加：Outcome選択と外観

- TaskのOutcomeは既存一覧（完了状態を表示）・Outcomeなし・新規作成から選ぶ。新規作成は名前のみ入力し、タスク保存時に期間なし・未完了で同時作成する。キャンセルでは作成しない。

- カテゴリとステータスの入力欄の大きさを揃える。詳細の閉じるボタンは右上に配置する。
- ツールイメージ/taskotter-logo-concept.pngを左上のロゴとブラウザタブのアイコンに使用する。


## 2026/10/02 18:20追加：Outcome表示とガント期間

- 新規Outcomeは既存の未分類Taskを紐づくTaskとして表示しない。紐づけのないTaskは新規Outcome作成後も未分類のままとする。
- Outcomeカードの全体から詳細を開く。カード内のTaskを押した場合はTask詳細だけを開く。
- ガントの表示期間は1週間・2週間（月曜始まり）、1ヶ月（暦月）、開始・終了日を指定する任意期間から選べる。初期は2週間。日数に応じてバー・区切り線を描画し、長い期間には横スクロールで対応する。
- Task・Outcome一覧とガントでは、親行を青系、Task行を白地として区別する。OUTCOME／TASKラベルも表示し、色だけに依存しない。


## 2026/10/02 18:50追加：Outcome行・月表示・Done非表示

- Task・Outcomeの階層一覧とガントのOutcome親行は、名前・期間・空白を含めて全体から詳細を開く。データのない「Outcomeなし」は編集対象としない。
- ガントの月表示は、年月と日番号を2段表示にし、月初から月末まで見渡せる幅にする。画面が狭い場合も横スクロールで月末まで確認できる。
- Task・Outcomeの階層一覧とカード内のDone Taskは初期非表示。「Doneも表示」で切り替えられる。ステータスでDoneを明示的に指定した場合も表示する。カードの進捗・完了件数は非表示のDoneを含む全Taskから計算する。


## 2026/10/02：Windowsの起動方式の更新

- Windowsの正式な起動手順はrun-windows.ps1をPowerShellから実行する。WSLは安定版へ更新し、wslc.exeが利用可能であることを確認する。公式情報確認時点の安定版はWSLパッケージ3.0.1（[公式リリース](https://github.com/microsoft/WSL/releases/tag/3.0.1)）。
- 保存先はWindows上の絶対ドライブパスを指定し、初期化・起動を分ける。保存先省略時はエラーとする。Ubuntu、wslpath、ホストのNode.jsは正式手順の依存に含めない。
- 既存のrun-windows.shはWSL利用者向けの任意の互換経路として保持する。


## WSL UbuntuのDocker Engineによる代替起動

- wslc.exeで起動できない環境向けに、WSL 2上のUbuntuへDocker Engineを導入し、run-wsl-docker.shから共通Containerfileをビルド・実行できるようにする。PowerShell／wslc方式も維持する。
- Windowsの保存先は/mnt/c/...形式で指定できる。Ubuntu内の保存先も指定可能。保存先省略はエラー。初期化は明示的かつ既存JSONを上書きしない。
- localhostにのみ公開し、Windowsのブラウザから操作する。停止・再開・削除・ログ・状態確認の手順を提供する。コンテナ削除では保存先を削除しない。
- Dockerのインストールは手順に沿って利用者が行う。スクリプトは自動インストール・権限設定・既存保存ファイルの所有者変更をしない。同じJSONを複数の実行方式から同時使用しない。
